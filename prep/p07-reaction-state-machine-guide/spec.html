Full specification

Required behavior

  1. For each member and topic/reply target, current reaction is absent, like (+1), or dislike (-1). A repeated same-value request leaves the current value unchanged.
  2. Setting the opposite value switches the row; clearing removes it. Clear is idempotent. Never allow both like and dislike rows for one member-target.
  3. Expose like and dislike counts for all visitors, including targets with no reactions; absent rows count as zero.
  4. Enforce target type and existence, a uniqueness constraint and a value CHECK; use one transaction per mutation.
  5. Bound SQLite busy waits and translate exhausted lock contention into a retriable error; do not await external I/O while holding a synchronous database transaction.

Inputs and output contracts

Out of scope

Build this focused deliverable, not the complete forum. Features in the Level up chapter are optional and are not prerequisites unless the roadmap explicitly selects them. Do not replace a core learning task with a framework or finished service.

Use synthetic users and disposable test data during development. Keep a decision record when the brief allows a choice; the record must include an independently verifiable consequence.
