Full specification

Required behavior

  1. Notify a post’s author when another member comments on it or changes a post reaction to like/dislike. Self-actions do not notify; repeated same-state reactions and clear operations do not notify.
  2. Persist the domain change and event in one SQLite transaction. Dispatcher creates the recipient notification and marks event delivered atomically with a unique event-recipient key.
  3. Use one documented single-instance dispatcher or drain command; reprocessing an event cannot duplicate a notification. A failed domain transaction produces no event.
  4. Inbox contains actor display name, action, time, safe target summary and current visibility-aware link. Only the recipient can read or mark their notification read.
  5. Use normal server-rendered refresh as the required delivery mode. Durable notifications work while the recipient is offline; real-time push is an optional separately prepared transport.
  6. Deleted or inaccessible target shows a tombstone without private content; if moderation is installed, pending activity must not leak in a public inbox link. Bound dispatch batches to 100 events.

Out of scope

Build this focused deliverable, not the complete forum. Features in the Level up chapter are optional and are not prerequisites unless the roadmap explicitly selects them. Do not replace a core learning task with a framework or finished service.

Use synthetic users and disposable test data during development. Keep a decision record when the brief allows a choice; the record must include an independently verifiable consequence.
