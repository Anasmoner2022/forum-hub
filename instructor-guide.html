Instructor delivery and assessment

Use the guides as build assignments, not reference-only reading and not finished solutions. Each preparation delivers a small working program or design, while each forum assignment combines already-demonstrated skills.

Cohort release checklist

  • Pilot P01–P12 with a learner who has the stated entry skills; revise time estimates from actual work.
  • Pin and test the Node patch, Docker runtime and specialist package lockfiles for the academy’s supported hosts.
  • Demonstrate both Google/GitHub live flows with approved test users; provide redacted setup worksheets and never distribute shared secrets in guide files.
  • Verify JPEG/PNG/animated GIF corruption and resource-boundary fixtures with the chosen Sharp version.
  • Rehearse local HTTPS trust on supported operating systems and container key permissions.
  • Measure scrypt latency and memory using the specified work factors and default single-job concurrency.
  • If selecting P21, verify the source-built SQLCipher binding inside Linux; Windows is a host, not a supported native binding target.
  • Assign mentors for Go readiness and equivalent behavior gates when teams select Go.
  • Freeze the coverage contract for the cohort and keep elective transports/providers outside mandatory scope.

Preparation exit gate

  • Artifact meets every specification row and verification case.
  • Automated checks include forbidden/failure paths; no TODO or skipped required checks remain.
  • Another learner reproduces it from the README, starting with a fresh test environment.
  • The learner explains one invariant and repairs an introduced bug without following a full solution.
  • Record readiness as assessed evidence, not as “guide generated” or “chapter read”.

Team of 4–5

Rotate ownership across storage, HTTP/authentication, rendering, operations and verification. Pair students across boundaries rather than permanently making one student the “database person”. Every member reviews code and demonstrates a component they did not initially write.

One-week extension rhythm

  1. Day 1: confirm its prep gate, migration and integration contract.
  2. Days 2–3: integrate the prepared feature and its failure paths.
  3. Day 4: run direct-request, privacy and installed-feature regressions.
  4. Day 5: peer audit, clean reproduction and individual explanation.

Critical failures block acceptance regardless of score: plaintext passwords, authentication bypass, private-content leak, silent partial writes, unreproducible Docker build or missing mandatory capability. Return the missing skill to the corresponding prep gate.

Submission evidence

  • Repository link and one chosen backend language.
  • ERD/schema/data dictionary and immutable migrations.
  • README with supported environments, configuration and run/test/container/restore commands.
  • Requirement-to-evidence checklist with case outputs and state checks.
  • Synthetic fixtures, no secrets, and redacted provider/certificate worksheets when applicable.
  • Team contribution record and individual demonstration.

Maintaining the curriculum

Edit the authored data in curriculum/ and rebuild with npm run build. Run npm run check afterward. Add prep before making a new technology mandatory. A content check validates curriculum structure and links; it does not certify completed student software. No Learning Hub catalog or completion record is changed by this workspace.
